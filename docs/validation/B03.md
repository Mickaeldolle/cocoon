# Validation B03 — runs durables de capture

Date : 2026-09-22

## Tranche livrée

- Ajout des modèles `CaptureRun` et `CaptureRunEvent`.
- Ajout de la migration `20260921_12_capture_runs.py`.
- Ajout de la migration `20260922_13_capture_idempotency.py`.
- Ajout de la migration `20260922_15_capture_worker_lease.py`.
- Une capture crée un run appartenant au même utilisateur.
- Le run enregistre `capture_persisted`, `understand_started`, puis `completed` avec le résultat borné.
- Le traitement partagé marque les erreurs en `failed` avec un code non sensible et permet un retry borné du même run.
- Les runs sont désormais `queued` avant claim, avec lease, owner de worker, compteur et maximum de tentatives.
- `app/commands/run_capture_worker.py` permet d’exécuter le traitement dans un processus séparé.
- `X-Capture-Idempotency-Key` réutilise un run terminé et empêche les doubles traitements concurrents.
- Chaque capture conserve une empreinte SHA-256 du contenu normalisé ; un retry sans clé réutilise maintenant le run terminé du même compte, tandis qu’un run identique actif est refusé explicitement.
- La réponse de capture retourne `run_id`.
- Chaque `NeuralProposal` produite par un run conserve désormais `source_run_id`, avec une migration additive et une clé étrangère vers `capture_runs`.
- `GET /api/runs/{run_id}` vérifie l’owner avant de retourner les événements.
- `GET /api/runs/{run_id}?after_sequence=N` permet une reprise incrémentale.
- `POST /api/runs/{run_id}/cancel` persiste l’annulation et l’événement associé.
- Le flux SSE émet immédiatement l’accusé `capture_persisted`, puis les événements persistés avec `id` et accepte `Last-Event-ID`.
- Le client mobile connaît le `run_id`, le contrat d’événement et la lecture d’un run.
- Le worker relit l’état durable après `understand` et avant l’insertion des propositions ; une annulation concurrente ne peut donc pas produire un commit tardif.
- `POST /api/captures/queue` persiste puis retourne un run `queued` en `202` sans exécuter le modèle ; le worker séparé peut reprendre le même run avec idempotence.
- Le client mobile expose également `neuralApi.queueCapture` pour utiliser ce mode worker sans contourner l’API.
- L’entrée universelle de `apps/mobile/app/home.tsx` utilise désormais le SSE reprenable comme chemin principal ; après une erreur réseau non liée à une erreur 4xx, elle réutilise la même clé d’idempotence pour mettre la capture en file worker et affiche l’état sous le champ.

## Limites restantes

- Le chemin HTTP traite encore immédiatement pour compatibilité MVP ; le worker séparé est disponible mais doit être choisi comme mode de déploiement pour une file asynchrone complète.
- La reprise SSE et la reconnexion bornée côté mobile sont implémentées ; leur validation réseau/appareil réel reste à effectuer.
- Après remontage de l’accueil, le mobile recharge le `run_id` conservé et interroge brièvement un run encore `queued` ou `running` avant de demander une nouvelle action ; il ne crée pas de seconde capture avec un nouvel identifiant pendant cette réconciliation.
- Le chemin accueil → SSE → propositions et le repli SSE → file worker sont vérifiés par le typecheck mobile ; la reprise visuelle après redémarrage de l’application n’est pas encore prouvée sur appareil.
- Le client persiste aussi la capture en cours dans `SecureStore` (ou `localStorage` sur web), mémorise le `run_id` dès le premier événement SSE et vérifie le run au remontage de l’accueil ; la validation sur fermeture forcée et redémarrage réel reste à effectuer.
- L’accueil expose une annulation explicite : le flux SSE est interrompu localement, puis `POST /api/runs/{run_id}/cancel` est appelé pour un run connu ; en cas d’échec de confirmation, le brouillon local n’est pas supprimé.
- Les retries et l’idempotence restent à tester sous concurrence PostgreSQL réelle.
- Aucun test PostgreSQL concurrent n’a encore été exécuté.
