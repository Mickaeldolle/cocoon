# Validation B01 — identité et isolation assistant

Date : 2026-09-22

## Tranche livrée

- Ajout de `apps/api/app/modules/assistant/context.py`.
- Centralisation de la récupération du thread, des messages récents, des mémoires actives et des tâches ouvertes.
- Chaque requête est filtrée par l’utilisateur authentifié avant tri et limite.
- Le module ne consulte pas le domaine `secret`, les conversations cachées ou les données familiales.
- Le chemin Hermes a été retiré du runtime assistant actif ; le provider local reste le seul contrat exposé.
- La matrice `User / FamilySpace / Conversation / Project / Memory / Task` est documentée dans `docs/security/access-matrix.md`.
- La matrice précise désormais explicitement `owner`, `scope` et la règle de lecture/mutation pour chaque ressource MVP, y compris la séparation famille/assistant et le périmètre secret.
- Les consentements sont versionnés et révocables via `/api/auth/consents`, avec isolation par compte.
- Le registre de politiques refuse désormais une clé inconnue ou une version obsolète ; les politiques MVP sont `assistant.memory`, `assistant.projects`, `assistant.voice` et `notifications.push`.
- L’enregistrement d’un token push exige désormais le consentement actif `notifications.push`; le mobile accorde ce consentement explicitement après la permission système et avant l’association du token.
- La révocation de `notifications.push` supprime immédiatement les tokens push de tous les appareils du compte et bloque toute nouvelle association tant qu’un accord n’est pas redonné.
- Les appareils du compte sont listables via `/api/auth/devices`; la révocation d’un appareil filtre `user_id`, révoque toutes ses sessions et supprime son token push.
- Le profil mobile affiche les appareils connectés et permet de révoquer les sessions distantes ; l’appareil courant reste explicitement identifié et n’est pas présenté comme révocable depuis cette vue.
- `tests/test_isolation.py` vérifie qu’un membre d’espace familial peut lire l’espace, qu’un non-membre reçoit 404, et qu’un utilisateur extérieur ne peut lire ni conversation ni messages par UUID.
- Les tests personnels et mémoire complètent cette preuve sur les objets strictement possédés par un compte.
- Le layout mobile purge les requêtes React Query non secrètes lorsque l’identité change ; les clés et données de la surface secrète sont conservées dans leur partition dédiée.

## Limites restantes

- Un probe PostgreSQL concurrent ciblé a été exécuté sur le verrouillage des propositions ; la matrice complète des routes et des transactions reste à qualifier sur une base dédiée.
- La révocation d’appareil est idempotente côté API ; l’interface mobile de gestion des appareils reste à brancher.
- Les RLS et la qualification PostgreSQL du modèle de consentement restent à implémenter.
- Les routes personnelles et familiales sont couvertes par des tests d’accès croisé SQLite ; la qualification PostgreSQL et l’audit complet de la matrice restent ouverts.
- Le lint mobile reste bloqué par `use-secret-gesture.ts`, hors périmètre volontaire de cette tranche.
- Les clés React Query des surfaces assistant, capture, mémoire, profil, notifications et données personnelles incluent désormais l’identifiant du compte ; les clés `secret` restent séparées et sont purgées indépendamment.
- Un probe PostgreSQL réel a été exécuté avec une proposition temporaire et deux transactions concurrentes : le verrou owner-scoped a produit exactement une confirmation initiale et un rejeu, puis toutes les données de probe ont été supprimées.
- Les listes et messages des conversations familiales ainsi que les espaces familiaux incluent également l’utilisateur dans leur clé de cache ; aucune clé de la messagerie secrète n’est réutilisée.
