# Validation B07 — rappels et notifications fiables

Date : 2026-09-22

## Tranche livrée

- Les récurrences utilisent une date d’échéance, un instant UTC et le fuseau de la règle ; les mois courts et les transitions DST passent par `zoneinfo`.
- Les migrations `20260922_16_notification_delivery.py`, `20260922_17_reminder_controls.py` et `20260922_18_notification_receipts.py` ajoutent les contrôles de livraison sans supprimer l’outbox existante.
- Le worker rattrape les occurrences manquées après arrêt, avec un plafond de douze occurrences par passage pour éviter une boucle infinie.
- La clé d’occurrence reste idempotente ; l’état de la règle et la création de l’outbox sont validés dans la même transaction.
- L’outbox possède une prise atomique par lease, un nombre d’essais, un backoff exponentiel borné et un état d’échec terminal non sensible.
- Les tickets de réponse Expo sont conservés séparément de `sent_at` ; les tokens `DeviceNotRegistered` sont désactivés.
- Le ticket interne conserve uniquement l’identifiant non secret du device pour relier un reçu asynchrone ; un reçu `DeviceNotRegistered` efface alors précisément son token.
- Plusieurs appareils sont envoyés dans le même lot ; un token invalide est désactivé sans empêcher l’acceptation du ticket pour les autres appareils.
- Un rappel reste conservé et consultable si aucun appareil n’est disponible ou si le fournisseur est indisponible.
- Les rappels récurrents peuvent être listés, modifiés ou annulés ; une occurrence future déjà mise en outbox est marquée annulée sans supprimer l’historique.
- Chaque utilisateur dispose d’un quota quotidien configurable pour éviter une boucle de notifications.
- Une occurrence récurrente n’avance pas lorsque le quota est épuisé ; elle reste consultable et livrable au cycle suivant.
- Un token d’enregistrement est limité au format Expo (`ExpoPushToken[...]` ou `ExponentPushToken[...]`) ; une valeur arbitraire est refusée avant association au device courant.
- Une notification sans device disponible passe directement en échec terminal `no_device` et reste consultable, sans retry inutile.
- Les notifications ciblant une tâche ouvrent maintenant la section personnelle des tâches via une route mobile allowlistée ; les autres cibles restent dans la liste des rappels au lieu d’être interprétées comme une route arbitraire.
- L’écran mobile `/notifications` liste les rappels personnels, expose les états vide/chargement/erreur et permet de marquer chaque rappel comme lu ; son accès est visible depuis l’accueil.
- Le client installe `expo-notifications`, configure le canal Android, demande la permission depuis l’inbox, enregistre le token auprès de `/api/auth/push-token` et ouvre l’inbox lorsqu’une notification est touchée.
- La déconnexion révoque le token push du device courant dans la même transaction que la session ; un ancien compte ne conserve donc pas la réception de rappels sur un appareil partagé.

## Limites restantes

- Un probe PostgreSQL ciblé a validé le verrouillage des propositions ; la concurrence complète des workers de rappels doit encore être confirmée sur une base dédiée.
- Les reçus Expo et l’ouverture vers une tâche/événement doivent encore être validés avec un appareil iOS/Android réel.
- `provider_ticket`, `provider_receipt`, `provider_status` et `read_at` distinguent maintenant acceptation, reçu fournisseur, échec de reçu et lecture utilisateur.
- Le polling réel des reçus Expo et l’ouverture vers une tâche/événement doivent encore être validés avec un appareil iOS/Android réel.
- La permission notification et l’arrivée réelle sur iOS/Android nécessitent encore un development build.
- Aucun `projectId` EAS réel n’est configuré dans cette copie (`eas.json` ne peut pas l’inventer) ; l’enregistrement échouera volontairement avec un message explicite tant qu’un development build associé au projet Expo n’est pas configuré.
