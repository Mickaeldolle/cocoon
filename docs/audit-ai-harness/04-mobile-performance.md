# 04 — Performance et expérience mobile

Audit du code Expo SDK 57. **Aucune durée de démarrage, taille de bundle, image par seconde ni latence Android n'a été mesurée**. Les points ci-dessous sont des chemins critiques déduits du code, pas des ralentissements reproduits. La validation doit se faire sur l'APK/development build concerné, avec le LLM réellement utilisé.

## Parcours initial observé

`app/_layout.tsx:21-44` monte QueryClient, charge la police et déclenche la restauration session/thème. `session-store.ts` vérifie le verrou biométrique local puis lit le refresh token et appelle `/api/auth/refresh` ; si l'API ancienne ne renvoie pas `user`, un `/me` séquentiel s'ajoute. `app/index.tsx:13-30` affiche un spinner jusqu'à `initialized`, puis redirige vers welcome/home/login. L'absence de mesure empêche d'attribuer la durée à la police, au stockage sécurisé, à la biométrie, au réseau ou au rendu.

Sur la conversation, l'historique et le catalogue de modèles sont chargés séparément. Le chat direct est accessible sans premier message. Le verrou du compositeur lié à `modelsReady` a été retiré : un catalogue lent ou indisponible n'empêche plus l'envoi avec le modèle serveur par défaut. Le chemin `home` envoie en streaming, met en cache bref la réponse et ouvre le chat ; l'écran chat possède sa propre mutation SSE et une bulle optimiste/retry. Un essai Expo Web local avec compte fictif et provider simulé a vérifié un envoi depuis `home`, la navigation vers le chat, la réponse en flux et l'envoi direct d'une suggestion. La base isolée contenait exactement deux messages utilisateur et deux réponses. Le parcours sur Android installé, les erreurs réelles et un provider vivant restent à vérifier.

Le client HTTP réessaie une requête authentifiée après refresh partagé (`src/stores/session-store.ts`, `src/services/api.ts`) et conserve le refresh token en SecureStore natif. Le store empêche maintenant une restauration, déconnexion ou rotation tardive du compte A d'écraser la session B ; les écritures du refresh token sont ordonnées. Trois tests de course asynchrone couvrent ces cas. L'accueil lit une éventuelle `pending-capture` héritée, mais aucun code courant n'enregistre ce brouillon ; ce chemin est gardé tant que les anciennes installations n'ont pas été qualifiées. Le message direct en cours n'est pas garanti après fermeture forcée. QueryClient est purgé lorsque l'application quitte un compte déjà actif ou change de compte (`app/_layout.tsx`) ; la première restauration `null → utilisateur` ne le purge plus, car elle annulait la requête initiale du lien direct `/memory` dans Expo Web local. L'écran assistant recrée maintenant son état local lorsque l'identité change, interrompt son flux au démontage et ignore les réponses arrivées pour l'ancien compte. Le paramètre de brouillon d'un lien direct reste lié au premier compte authentifié sur cette route pour éviter un envoi sous le suivant. Un essai Expo Web local A→déconnexion→B a affiché la bulle d'A seulement sous A ; la base de test contenait un message A et aucun message B. Le mode hors ligne est partiel : l'historique utilise le cache mémoire de React Query pendant la session ; aucun stockage durable de conversations hors ligne n'est établi. L'erreur d'historique est affichée dans l'assistant, mais le parcours de reprise et la distinction « hors ligne / serveur / provider » restent à qualifier sur appareil.

## Plan de mesure avant optimisation

Instrumenter, avec identifiant de session pseudonyme et sans texte de message : démarrage natif→premier écran utile, durée restauration locale, refresh, navigation home→chat, temps jusqu'à saisie active, requête historique, catalogue modèles, premier octet SSE, premier delta visible, fin de réponse, re-render de la liste. Capturer p50/p95 sur dix parcours par profil de réseau (local, Wi-Fi médiocre, hors ligne), à froid et à chaud, sur l'appareil cible. Côté serveur, corréler request ID avec SQL/LLM. Séparer réseau API, attente LLM et rendu, puis choisir un budget après baseline ; aucun chiffre cible chiffré n'est inféré du dépôt.

## Changements proposés

| Priorité | Intervention | Compromis et validation |
| --- | --- | --- |
| P1 corrigé localement | La saisie fonctionne sans attendre le catalogue ; sélection avancée facultative. | Le backend revalide le modèle demandé. Vérifier catalogue lent/503, compte autorisé et révoqué sur navigateur/appareil. |
| P1 | Garder l'écran et le compositeur visibles pendant les requêtes ; état local précis « conversation en chargement », retry explicite. Preuve `assistant.tsx:437-450`. | Éviter une réponse ancienne après changement de compte ; tester A→B et erreur 401. Complexité faible. |
| P1 | Mesurer et, si besoin, réduire les étapes séquentielles de restauration (refresh + `/me` ancien) et les requêtes au focus (`_layout.tsx:45-54`, `home.tsx:89-92`, `assistant.tsx:120-123`). | Conserver la révocation serveur et la fraîcheur de `enable_assistant`. Tester ouverture froide, arrière-plan, token expiré. Complexité moyenne. |
| P2 | Profiler le rendu des longs historiques ; pagination/virtualisation seulement si le profilage montre un coût. `assistant.tsx:430-540` rend dans `ScrollView`. | Préserver l'ancrage bas, les bulles optimistes et le clavier ; test de 10/100/500 messages sur Android. Complexité moyenne. |
| P2 | Instrumenter la première réponse SSE et les états réels (connexion, génération, erreur). `assistant/router.py:585-642`, `api.ts:740-810`. | Ne pas afficher une étape « mémoire » si elle n'a pas eu lieu ; test LLM lent, annulation, reprise. Complexité faible/moyenne. |

La politique de cache doit rester par utilisateur, avec invalidation après mutation et purge à la déconnexion. Éviter de persister l'historique secret ou les prompts privés dans un cache durable. Toute optimisation de démarrage dépendra d'une mesure native ; une capture navigateur ne démontre pas la performance Android.
