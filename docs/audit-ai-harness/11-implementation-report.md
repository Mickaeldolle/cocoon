# 11 — Rapport d'exécution de la roadmap

État du 8 octobre 2026. Périmètre : worktree courant, documents 01–10, `docs/VISION.md`, API FastAPI, client Expo, workers, migrations, Compose et CI. Les changements de mémoire déjà présents dans le worktree ont été revus ; les corrections ci-dessous complètent ce travail. Les résultats locaux ne valent pas qualification d'un environnement déployé.

## Décisions d'architecture

- Garder le monolithe modulaire, PostgreSQL, les workers existants et l'assistant conversationnel comme premier parcours. La mémoire reste personnelle et soumise à confirmation ; le partage familial et l'agentivité restent des étapes distinctes de la vision.
- Filtrer les souvenirs autorisés en SQL avant le classement, conserver le repli lexical et laisser embeddings/pgvector désactivés tant que leur qualité et leur exploitation ne sont pas prouvées.
- Garder l'autorisation côté serveur. Les helpers extraits ne modifient ni les routes publiques, ni les formats SSE, ni le transport mobile et sa promesse unique de refresh.
- Traiter la migration welcome comme une révision de `main` déjà fusionnée avant le rebase. La migration mémoire suit cette révision ; aucune réécriture de la migration welcome n'est nécessaire.

## Mesures et portée des vérifications

Un essai Expo Web avec compte fictif, API locale et flux modèle déterministe a vérifié le premier envoi depuis `home`, la navigation vers le chat, la réponse affichée et l'envoi direct d'une suggestion. Deux tours utilisateur et deux réponses ont été constatés dans la base SQLite jetable, sans duplication. Le flux capture, la gestion d'erreurs, le clavier Android et la latence du modèle réel restent à qualifier.

Le benchmark `docs/validation/memory-benchmark.json` utilise une base SQLite isolée et cinq questions par taille de corpus. Son rappel global est 0,8 aux quatre tailles ; une paraphrase sur deux échoue. La médiane de requêtes SQL par retrieval est 2, avec un maximum de 3 dans cet essai. Les latences de ce fichier décrivent le banc synthétique local, pas la production. Les tests PostgreSQL acceptent une base jetable `_test`/`_ci` ou, avec `MEMORY_TEST_LOCAL_SCHEMA=1`, un schéma temporaire sur le PostgreSQL local `cocoon` ; les deux tests vectoriels exigent l’extension `vector`. Ne jamais les pointer vers une base Supabase contenant des données personnelles.

Lors de cette passe, le binaire `ollama` était absent du `PATH`, `127.0.0.1:11434` ne répondait pas et aucun `adb` n'était disponible. Le banc de contexte avec un provider vivant et les essais sur Android installé n'ont donc pas été exécutés ; leurs critères restent dans la roadmap.

La suite API complète donne **237 tests réussis, 2 ignorés** (les deux cas pgvector, absent du serveur local) ; Ruff passe sur tout `apps/api`, y compris le point d'entrée Vercel. Le client donne **39 tests réussis** ; TypeScript, ESLint et Prettier passent sur les écrans modifiés, et l'export web Expo local passe après la vérification du parcours mémoire. La commande `expo lint` n'a pas démarré localement car `npx` manque dans le PATH de ce shell ; la même analyse a été exécutée directement avec ESLint. La migration complète a aussi été exécutée sur PostgreSQL 14 dans un schéma temporaire, avec descente et remontée de la révision mémoire. Le moteur Docker, pgvector et le CLI PostgreSQL local restent indisponibles ; le serveur PostgreSQL local est accessible par le pilote Python. Restent à enregistrer séparément : CI PostgreSQL avec pgvector, contexte et qualité avec Ollama vivant, autres parcours navigateur (capture et notifications), expérience Android development build, puis sauvegarde/restauration et surveillance sur l'hébergement réel.

## Déploiement et sécurité

Le [runbook mémoire](../deployment-memory.md) couvre la base locale, Vercel + Expo web avec Supabase, puis le VPS Docker. Sur Supabase, vérifier les droits du schéma `public` et la Data API avant toute donnée personnelle. Sur Vercel, ne pas activer la recherche vectorielle tant que l'API n'a pas un accès privé et authentifié au service d'embeddings. Sur VPS avec Supabase, séparer le rôle DDL du migrateur du rôle DML de l'API et des workers ; vérifier leurs permissions effectives après migration. Qualifier l'extension pgvector, la migration, le worker, les secrets, les sauvegardes et le rollback sur copie jetable avant activation.

L'oubli du contexte futur ne constitue pas un effacement immédiat de toutes les sources et sauvegardes. Le [runbook](../deployment-memory.md) distingue désormais ces classes de données et prescrit un essai de restauration sur une seconde base isolée. Les durées de rétention, la purge physique, une restauration exécutée, les anciens contenus non traçables et les permissions des opérateurs restent à décider et à vérifier avant toute promesse d'effacement complet.

## Prochaines portes de sortie

1. Confirmer la CI PostgreSQL avec pgvector, les droits de rôles et la reprise du worker sur une base jetable ; comparer ses plans au relevé local.
2. Tester un corpus caché avec paraphrases, contradictions, inconnus et petits contextes sur le modèle local choisi. Mesurer rappel, précision, tokens, réponse et latence ; ajuster FTS ou introduire pgvector seulement sur gain établi.
3. Vérifier les parcours mémoire, chat et profil dans le navigateur et sur Android ; tester Expo Push réel avec deux comptes, révocation et application fermée.
4. Sur chaque hébergement, vérifier secrets, privilèges Supabase, migration, sauvegarde/restauration, supervision et rollback ; décider la rétention des sources et tester le rejeu des effacements après restauration d'une copie antérieure à l'oubli.
5. Après les parcours UI, reprendre le découpage du chat et de `conversation-detail-screen.tsx` par état/effet ou rendu cohésif, en conservant le contrat secret, les retries et le refresh partagé. Inventorier les données de la colonne Hermes avant toute suppression de schéma et vérifier les imports externes avant distribution.

Ces étapes sont des critères de qualification, pas des conditions pour conserver les correctifs déjà testés localement.
